Baseline: `9db5dfc` on `main`, reviewed 2026-10-05.

Goal: a complete, locally hosted video-management demo that demonstrates Floci's S3, SNS, SQS, and Lambda integration, including failures and recovery. `PROJECT.md` remains the canonical description of implemented architecture. This file describes planned work, acceptance criteria, dependencies, and delivery status; proposals are not existing features.

## Priorities and delivery rules

- **P0 — Blocking defects:** fresh setup, build, or ordinary upload/playback can fail or lose results.
- **P1 — Release requirements:** reliable recovery, video management, repeatable setup, and end-to-end validation.
- **P2 — Showcase requirements:** polished presentation, inspectable service behavior, and community packaging.
- **P3 — Optional extensions:** useful after the complete local demo ships.

Items are ordered by priority, then recommended sequence within each priority. Dependencies override sequence: a supporting P1 item may be implemented before a P0 item that depends on it. IDs are stable. Every item starts **Ready** unless marked otherwise; Ready means scoped for implementation, not implemented. The release requires P0–P2; P3 is explicitly deferred.

Use one branch and one PR per bounded change. An item can have several PRs when it crosses backend, worker, and frontend contracts. Keep dependent branches explicitly stacked until their prerequisites merge; then rebase onto `main`. Do not merge automatically. Record exact validation and any outstanding local verification in the PR. Update this backlog, `PROJECT.md` when applicable, and `CHANGELOG.md` in each implementation.

## Implementation conventions

- Java 25 / Spring Boot: existing packages, constructor injection, records for DTOs, Bean Validation, ProblemDetail errors, jOOQ repositories, conditional transactional updates. Introduce forward migrations; never edit applied V1 to evolve schema and never hand-edit generated jOOQ sources.
- Vue: feature-based API/composable/UI layout, TypeScript, `<script setup>`, Tailwind, existing error helpers and Vitest/Vue Test Utils conventions. Keep transport/state out of presentation components. Do not introduce another frontend framework or state library without a concrete need.
- Lambda: preserve native `Consumer<byte[]>` handling until a tested reason requires change; keep `ProcessBuilder` argument lists, shared fixtures, and compatible message/key contracts. Validate both JVM tests and deployed native execution when changing serialization or packaging.
- Infrastructure: maintain shell and PowerShell parity; preserve existing resources on repeated bootstrap; do not put source configuration in generated artifacts.
- Testing: choose regression cases for changed behavior, not implementation-mirroring tests. Unit tests do not replace PostgreSQL/Floci integration for concurrency or deployed E2E for native Lambda/media delivery.
- Compatibility: API/message/schema changes include rollout and migration notes. Database and object cleanup must be retryable; deletion and retries must reject stale work.

## Review and release process

1. Select the highest-priority item with satisfied dependencies and define one reviewable slice.
2. Branch from current `main` or explicitly declare the prerequisite branch. Commit only scoped code, meaningful regression coverage, and required documentation.
3. Create ready-for-review PRs, including stacks when needed. The agent handles scoped commits; the user reviews, supplies local verification when needed, and merges. PR explains the user-visible defect, resulting behavior, validation actually run, remaining manual checks, and task ID. No automatic merge.
4. Reviewer runs any missing local checks; record results before marking **Done**. `Implemented / awaiting local verification` is distinct from `Done`.
5. After merge, rebase dependent branches, update task state, and continue. Independent small fixes may proceed while integration work is blocked.
