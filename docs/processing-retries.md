# Processing retries: local acceptance

PR #22 is stacked on backend PR #21. Test `feat/sa-013-processing-retry-ui` to get both, then merge #21 before #22. The worker contract is the already merged PR #18 version, whose explicit-attempt native replay the user verified. This check exercises the new API/outbox/UI path end to end.

1. Stop any older launcher with Ctrl+C. Check out this branch and run `./run-local.sh` on Linux, or `powershell -NoProfile -ExecutionPolicy Bypass -File .\run-local.ps1` on Windows. The backend applies V5; the runner reuses unchanged native worker sources/layer. No data reset or manual completion message is needed.
2. Open http://localhost:5173 and the Stream tab. Choose a disposable FAILED video whose original upload exists. The previously tested `5ae39b91-aa53-476c-a877-21cb49c6bd79` is usable if it is still FAILED and its source remains present. Ready/active videos must not offer Retry processing.
3. Click **Retry processing**. While the request is pending, the action is disabled. Browser network traffic should show `POST /api/v1/videos/{id}/processing-retries` returning 202 with a new attemptId. There must be no new registration or file PUT. The library becomes processing and refreshes automatically. QUEUED means saved intent, not a claimed worker start.
4. Let the real Lambda run. Open `http://localhost:8080/api/v1/videos/{id}/attempts` using the actual UUID. The new active attempt should have queuedAt and eventually SUCCEEDED/FAILED plus completedAt. Previous attempts keep their existing timestamps/reasons. Source bytes and public video ID are unchanged. Invalid source bytes may correctly fail again; retry does not repair media. If a known-valid failed source recovers to ready, verify playback and seeking use the new successful artifact.
5. Refresh/restart using the launcher; history/state and existing ready playback must remain. Multiple concurrent requests can produce only one active retry; the additional request receives 409 and refreshes current state. A missing original source gives an actionable 409 without creating an attempt; do not delete a real source just to test this (covered automatically).

Report request acceptance, new history/terminal result and retained old playback. If a request's response is lost, the UI refreshes to reconcile actual state; acceptance is never assumed after a network error. It may show a request error until another action/refresh while server state resolves. The existing original-notification native probe remains separately unreported; it is not inferred from this UI check.

The outbox persists the exact command in the same transaction as retry creation. PostgreSQL/Floci tests cover unavailable SQS, retry backoff, restart/claim expiry, concurrent claims and identical resend after an accepted send whose DB acknowledgment was lost. No exactly-once queue guarantee or outbox/DLQ-to-status reconciliation is claimed. Delayed dispatch preserves QUEUED; DLQ arrival does not itself settle the video (later SA-015).
